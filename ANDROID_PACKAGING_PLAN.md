# Пункт 36. План упаковки игры в Android-приложение

Дата проверки: **12 ноября 2026 года**. Исходная версия игры: **3.6.1**.

Это документ для выбора способа сборки. Android-проект, APK и ключ подписи пока не создавались; зависимости игры не менялись. **Весь план относится только к Android.** Подготовка и сборка iOS сюда не входят.

## 1. Что выбрать для этой игры

Для **небольшого APK, который работает без интернета сразу после установки**, первым я бы проверил **вариант A: собственная обёртка Android WebView**. Если важнее сократить ручную работу с Android и проще добавлять функции телефона — **вариант B: Capacitor**. Это два основных кандидата для нашего проекта.

**Tauri 2** тоже поддерживает Android и подходит как альтернатива подходу Electron, но потребует Rust и более сложной среды сборки. **TWA/Bubblewrap** имеет смысл, если игра прежде всего будет опубликованным сайтом: маленькая оболочка открывает его через браузер.

Ожидаемый порядок по размеру ниже — инженерная оценка, а не результат сборки нашей игры. Сравнивать нужно подписанные release-артефакты с одинаковыми ресурсами и поддерживаемыми архитектурами.

| Вариант | Где выполняется игра | Первый запуск без интернета | Хостинг | Оценка для нашей задачи |
| --- | --- | --- | --- | --- |
| **A. Android WebView + локальный билд** | Системный Android WebView | Да, если все ресурсы упакованы | Не нужен | Кандидат на наименьшую автономную оболочку; больше кода обёртки вручную |
| **B. Capacitor** | Системный Android WebView | Да, при локальной сборке | Не нужен | Удобный основной вариант; готовый мост к Android и плагины |
| **C. Tauri 2** | Системный Android WebView + native-часть Rust | Да, при локальной сборке | Не нужен | Больше инструментов; меньший размер относительно A/B не гарантирован |
| **D. TWA + Bubblewrap** | Совместимый установленный браузер | Не гарантирован; нужен ранее заполненный веб-кеш | Нужен HTTPS-сайт | Небольшой APK, но игра и её кеш загружаются отдельно |

Системный WebView или браузер не включаются целиком в эти APK. Их собственный размер при этом существует на устройстве отдельно. Замена оболочки сама по себе не превращает Three.js в нативный игровой движок и не гарантирует рост FPS. [Capacitor Android](https://capacitorjs.com/docs/android), [WebView в Tauri](https://v2.tauri.app/reference/webview-versions/), [Android TWA](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities).

## 2. Что уже есть и что потребуется проверить

По текущим файлам проекта:

- Игра использует React, Vite, React Three Fiber и Three.js `0.184.x`; сцены и модели остаются прежними при упаковке.
- Есть сборка `npm.cmd run build`, сенсорное управление, локальные оптимизированные OGG-звуки, сохранение профиля и настроек.
- `vite.config.js` пока не содержит специальной Android-конфигурации. В текущем `dist/index.html` ссылки на ресурсы начинаются с `/assets/`.
- Android-проекта и service worker в исходниках пока нет.
- В существующей папке `dist/assets` обнаружено **98 файлов общим размером около 90.6 МБ**, включая 62 JS-файла разных прошлых сборок. **Это не размер актуальной игры:** при упаковке нельзя просто скопировать всё накопленное содержимое. Нужна свежая отдельная сборка и синхронизация каталога ресурсов.
- В последнем отчёте сборки основной JS занимал около **1.65 МБ без сжатия**. Итоговый размер APK пока неизвестен: к веб-ресурсам добавятся Android-код, ресурсы оболочки и подпись.

Для нашей версии Three.js требуется **WebGL 2**. Поэтому совместимость определяют не только номер Android и `minSdk`, но и версия WebView, GPU и драйверы. Нужна проверка реального устройства и понятное сообщение при отсутствии WebGL 2. [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

## 3. Общая подготовка перед любым вариантом

1. **Зафиксировать исходную рабочую версию.** Выбранную оболочку делать в отдельной ветке. Варианты ниже альтернативные: не нужно устанавливать все четыре в один проект.
2. **Выбрать идентификатор приложения**, название, иконку и правила версий. Пример `com.example.hpproject` в командах временный; финальный идентификатор следует определить до распространения приложения.
3. **Подготовить Android-среду:** Android Studio, совместимый JDK, SDK Platform, Build Tools и Platform Tools. Для Tauri дополнительно нужен NDK и Rust. Версии SDK/Gradle/JDK согласовать с выбранной оболочкой; `targetSdk` для магазина перепроверить перед публикацией.
4. **Получать отдельную чистую веб-сборку.** Например, `dist-android`, добавить её в `.gitignore`, копировать только её содержимое. Не упаковывать `node_modules`, исходные WAV, тесты, документацию и старые hash-файлы из `dist`.
5. **Проверить пути загрузки.** Для локального WebView использовать относительную базу `./` либо строго согласовать абсолютную базу с загрузчиком. Особенно проверить импорт звуков и их загрузку через `fetch`. У Vite база меняет ссылки на собранные ресурсы. [Vite: Public Base Path](https://vite.dev/guide/build.html#public-base-path).
6. **Определить поведение оболочки:** системная кнопка/жест «Назад», пауза при уходе в фон, звук после возврата, вырезы экрана и системные панели. Портрет и альбомную ориентацию проверить отдельно; принудительную ориентацию выбирать после проверки существующего интерфейса.
7. **Проверить сохранения.** Нужны постоянный origin и хранение DOM Storage. Прогресс из браузера на ПК автоматически в установленное приложение не переносится. Сохранение текущего раунда после уничтожения процесса — отдельная функция; наличие сохранённого профиля её не заменяет.
8. **Собрать тестовый APK и пройти проверки из раздела 9**, затем настраивать подпись и измерять release-размер.

## 4. Вариант A — собственная Android WebView-обёртка

### Устройство приложения

Одна Android Activity содержит WebView. Внутри APK лежит готовая HTML/JS/CSS-сборка и звуки. Она загружается через `WebViewAssetLoader` по локальному HTTPS-origin; настоящий веб-сервер для запуска не нужен. Android рекомендует этот способ для локального веб-контента. [Загрузка встроенного контента](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content).

### План выполнения

1. Создать минимальный Android-проект на Kotlin или Java в папке `android/`. Для одной WebView достаточно обычной Activity; дополнительная UI-библиотека оболочке не требуется.
2. Выбрать `minSdk` по результатам проверки целевых телефонов. Проверить актуальный системный WebView и WebGL 2; один номер SDK не является гарантией совместимости.
3. Добавить AndroidX WebKit для `WebViewAssetLoader`. Зафиксировать совместимую версию зависимости.
4. Собрать игру с относительными путями в отдельный каталог:

   ```powershell
   # Из корня hpproject, после создания выбранного Android-проекта.
   npm.cmd run build -- --base=./ --outDir dist-android
   ```

5. Настроить Gradle-задачу синхронизации: **содержимое** `dist-android/` → `android/app/src/main/assets/www/`. Она должна удалять устаревшие файлы только в своём целевом каталоге `www`, не затрагивая остальные Android-ресурсы. Подключить её перед Android-сборкой.
6. Подключить `WebViewAssetLoader` и открыть `https://appassets.androidplatform.net/assets/www/index.html`. Проверить корректные MIME-типы модулей, CSS и OGG. Не основывать загрузку модулей и звука на `file://` и ослаблении ограничений доступа к файлам.
7. Включить JavaScript и DOM Storage. Сохранить аппаратное ускорение. Подключить `WebViewClient`, а для диагностики — `WebChromeClient`. WebView-debugging включать только в отладочной сборке. Настройки DOM Storage по умолчанию выключены. [WebView](https://developer.android.com/develop/ui/views/layout/webapps/webview), [WebSettings](https://developer.android.com/reference/android/webkit/WebSettings#setDomStorageEnabled(boolean)), [аппаратное ускорение](https://developer.android.com/topic/performance/hardware-accel).
8. Добавить небольшой lifecycle-мост: уход в фон ставит обе игровые сцены на паузу и останавливает звук; возврат не проигрывает накопившееся время. Первый тап должен разрешать запуск AudioContext. Системный Back должен приводить к понятному игровому действию, а не случайному закрытию приложения.
9. Проверить fullscreen/insets, жесты возле нижнего края, touch-перенос предмета и отмену касания. Дизайн игровых меню сохранять.
10. Собрать debug APK и установить на телефон. После успешной проверки настроить release-подпись, оптимизацию Android-кода и ресурсов.
11. Получить подписанный APK для прямой установки; при необходимости публикации в Google Play — AAB. Измерить размер и запуск. Обновление локальной игры распространяется новым APK/AAB.

Команды после настройки проекта и синхронизации ресурсов:

```powershell
# Из папки android.
.\gradlew.bat assembleDebug
.\gradlew.bat installDebug

# После отдельной настройки release-подписи.
.\gradlew.bat assembleRelease
.\gradlew.bat bundleRelease
```

Обычно debug APK находится в `android/app/build/outputs/apk/debug/`, release APK — в `outputs/apk/release/`, AAB — в `outputs/bundle/release/`. Конкретные имена зависят от Gradle-вариантов. [Сборка через Gradle Wrapper](https://developer.android.com/build/building-cmdline).

**Результат варианта:** автономная игра с минимальной собственной Android-обвязкой. Все дополнительные функции телефона и обработку жизненного цикла поддерживаем самостоятельно.

## 5. Вариант B — Capacitor

Capacitor подключается к существующему React/Vite-проекту и создаёт Android-оболочку с готовым мостом к платформе. Переписывать игру на Ionic или устанавливать Ionic UI не требуется. В APK копируется локальная веб-сборка. [Установка Capacitor](https://capacitorjs.com/docs/getting-started).

### План выполнения

1. Проверить требования выбранной версии. Для актуальной ветки Capacitor 8 указаны Node.js 22+ и Android Studio 2025.2.1+; перед установкой ещё раз сверить среду. Наш Node.js 24 подходит по этому порогу. [Требования Capacitor](https://capacitorjs.com/docs/getting-started/environment-setup).
2. Установить совместимые версии `@capacitor/core`, `@capacitor/cli` и `@capacitor/android`, зафиксировать их lock-файлом. Не подключать плагины заранее без необходимости.
3. Инициализировать оболочку. В `capacitor.config.*` указать финальные `appId`, `appName`, **`webDir: 'dist-android'`**. Каталог должен совпадать с фактическим выходом Vite.
4. Создать Android-проект, собрать веб-игру и синхронизировать ресурсы. Пример последовательности для совместимой ветки 8:

   ```powershell
   # Из корня проекта; команды выполняются при выборе варианта B.
   npm.cmd install @capacitor/core@8 @capacitor/android@8
   npm.cmd install -D @capacitor/cli@8
   npx.cmd cap init
   # Затем задать webDir: 'dist-android' в конфигурации.
   npm.cmd run build -- --base=./ --outDir dist-android
   npx.cmd cap add android
   npx.cmd cap sync android
   npx.cmd cap open android
   ```

5. Настроить иконки, системные панели, Back и lifecycle. При необходимости добавить только соответствующие плагины App/Status Bar и обработчики в игре. Игровой интерфейс остаётся текущим.
6. Убедиться, что release использует локальный `webDir`, без адреса dev-сервера в `server.url`. Проверить первый запуск в авиарежиме, загрузку всех звуков и сохранения.
7. Запустить на телефоне через Android Studio или `npx.cmd cap run android`; пройти общую проверку WebGL/touch/звука/фона.
8. Настроить подпись и release-оптимизацию в Android-проекте. Собрать APK/AAB через его Gradle Wrapper, как в варианте A; замерить размер.
9. Для каждого обновления выполнять: веб-сборка → `cap sync android` → Android-сборка. `cap sync` копирует готовый веб-билд, но не заменяет `vite build`. [Рабочий цикл Capacitor](https://capacitorjs.com/docs/basics/workflow), [Android-проект](https://capacitorjs.com/docs/android).

**Результат варианта:** автономное приложение с более удобным подключением Android-функций. Есть дополнительные зависимости оболочки; разницу размера с A нужно измерить.

## 6. Вариант C — Tauri 2

Tauri 2 поддерживает Android и использует на нём системный Android WebView. **Windows WebView2 к Android APK отношения не имеет.** Tauri не требует поставлять свой Chromium, но добавляет нативную Rust-часть. Для этой игры это прежде всего другой способ упаковки, а не автоматическая оптимизация Three.js. [WebView Tauri](https://v2.tauri.app/reference/webview-versions/).

### План выполнения

1. Установить совместимую среду: Rust/rustup, нужные инструменты Windows для сборки, JDK, Android SDK и NDK. Настроить пути и Android Rust targets по официальному руководству. [Требования Tauri](https://v2.tauri.app/start/prerequisites/).
2. Добавить Tauri 2 CLI и создать минимальный `src-tauri/` через `npx.cmd tauri init`. Сохранить существующий React/Vite-код.
3. Указать `build.frontendDist: '../dist-android'`, команду предварительной production-сборки Vite с `--outDir dist-android` и согласованной базой. Для разработки настроить dev URL/порт по руководству, не переносить dev URL в release. [Tauri + Vite](https://v2.tauri.app/start/frontend/vite/).
4. Задать identifier приложения и выполнить `npx.cmd tauri android init`. Добавить иконки, проверить Android SDK/NDK и сгенерированную конфигурацию.
5. Запустить `npx.cmd tauri android dev`; при необходимости открыть Android Studio через `npx.cmd tauri android dev --open`. [Разработка Tauri](https://v2.tauri.app/develop/).
6. Настроить только нужные capabilities/плагины, lifecycle, Back и fullscreen. Проверить загрузку локальных ресурсов, WebGL 2, звук и сохранения.
7. Настроить Android-подпись и собрать release. Для сравнения размера учитывать архитектуры: универсальный APK с несколькими ABI нельзя напрямую сравнивать с APK только для ARM64.

   ```powershell
   # Из корня проекта после настройки варианта C и release-подписи.
   npx.cmd tauri android build --apk
   npx.cmd tauri android build --aab
   # При необходимости отдельных APK по архитектурам:
   npx.cmd tauri android build --apk --split-per-abi
   ```

8. Проверить полученный APK на телефоне, измерить размер, время старта и память. Оставлять Tauri имеет смысл при пользе от его native-части или общего направления развития, а не на основании предполагаемого выигрыша в мегабайтах. [Android-сборка и подпись Tauri](https://v2.tauri.app/distribute/google-play/).

**Результат варианта:** локальная WebView-игра в Tauri с Rust-частью. Подготовка среды сложнее A/B; для одной текущей Android-игры это запасной вариант.

## 7. Вариант D — TWA + Bubblewrap / опубликованная PWA

Trusted Web Activity открывает опубликованную игру через совместимый браузер без обычной панели браузера после проверки связи приложения с доменом. Здесь основной продукт — HTTPS-сайт; его файлы не превращаются автоматически во встроенные ресурсы APK. Офлайн зависит от service worker и сохранённого кеша. [TWA overview](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities).

### План выполнения

1. Выбрать HTTPS-хостинг и домен, на котором можно разместить игру и `/.well-known/assetlinks.json`.
2. Подготовить сайт: web manifest, название, иконки, start URL, fullscreen/display-настройки.
3. Добавить service worker с версиями кешей для HTML, JS, CSS и всех необходимых звуков. Продумать обновления и очистку старых кешей, чтобы не смешивались версии игры.
4. Проверить PWA в Android-браузере: онлайн-запуск, офлайн после кеширования, обновление, удаление кеша. Свежая установка без сети не должна заявляться как поддерживаемая, если данные ещё не загружались.
5. Создать отдельный проект оболочки Bubblewrap из URL manifest:

   ```powershell
   # После установки Bubblewrap CLI и подготовки HTTPS-сайта.
   bubblewrap init --manifest=https://example.com/manifest.webmanifest
   ```

6. Настроить package ID, подпись и Digital Asset Links. В `assetlinks.json` должны быть корректные SHA-256 отпечатки сертификатов установленного приложения. При Play App Signing учитывать сертификат подписи приложения, а не только upload key.
7. Собрать через `bubblewrap build`, установить через `bubblewrap install`. Проверить подтверждение домена и отсутствие браузерной панели; отдельно проверить поведение при неподтверждённом домене или отсутствии подходящего браузера. [Bubblewrap quick start](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start).
8. Подготовить подписанный APK для тестов и AAB для Google Play. Проверить общий объём: оболочка **плюс загруженная игра и браузерный кеш**.
9. Обновлять игру на хостинге через управляемое обновление service worker. Саму Android-оболочку пересобирать при изменении её настроек.

**Результат варианта:** приложение для запуска веб-версии. Подходит для сайта с дополнительным Android-каналом распространения; для полностью автономной поставки первым выбором остаются A/B.

## 8. Почему не Electron и какие ещё варианты есть

- **Electron** официально предназначен для Windows, macOS и Linux; он поставляет Chromium и Node.js. Официальной сборки под Android нет. Для APK этой игры его не выбираем. [Официальное введение Electron](https://www.electronjs.org/docs/latest/).
- **Cordova** технически подходит для упаковки веб-игры в Android WebView. Для нового проекта без зависимости от конкретного Cordova-плагина я предпочёл бы Capacitor: это рекомендация по удобству для нашего проекта, а не утверждение, что Cordova заброшен. [Cordova Android guide](https://cordova.apache.org/docs/en/latest/guide/platforms/android/).
- **Flutter / React Native с WebView** добавят ещё одну платформенную оболочку вокруг той же игры. Перенос в их собственный рендерер — отдельная переработка, а не упаковка текущего `dist`. В рамках цели «маленький APK без переписывания игры» причины начинать с них пока нет.

## 9. Проверки перед готовым APK

Один и тот же набор проверок нужен для A/B/C; для D офлайн проверяется с учётом предварительного кеширования.

1. Первый запуск после установки; меню открывается без обращения к `localhost:5173` и dev-серверу.
2. Авиарежим: оба игровых режима, магазин, бестиарий, обучение, локальные звуки и модели доступны.
3. WebGL 2 и сцены на реальном телефоне; отсутствие чёрного экрана и ошибок контекста. Эмулятор подходит для первичной проверки, но не заменяет GPU/нагрев/производительность телефона.
4. Сенсорное управление: выбор всех мелких целей, касты, перенос рядом с объектом, каст вдали, сброс, второй палец, отмена касания, отсутствие читов.
5. AudioContext запускается после первого настоящего касания; звук регулируется и выключается; после возврата из фона нет одновременного проигрывания старых эффектов.
6. Уход в фон, блокировка экрана и возврат не расходуют время раунда и не вызывают скачков анимации. Потеря WebGL-контекста и уничтожение процесса обрабатываются предсказуемо.
7. Сохранённый профиль, stones, покупки и настройки переживают обычный перезапуск и установку обновления поверх предыдущей версии с той же подписью. Удаление приложения/очистка его данных — отдельный сценарий потери локальных данных.
8. Системный Back, вырезы и нижняя навигационная область не мешают кнопкам и заклинаниям. Проверить портрет, альбом, разные пропорции и изменение размеров.
9. Пройти несколько волн защиты и рецепт с врагами; проверить FPS, память, нагрев и расход батареи. Имеющиеся ограничения DPR/частиц сохранить, менять качество по результатам измерений.
10. Повторить ключевые проверки на **release**, особенно после R8/resource shrinking; успешный debug-запуск не доказывает исправность release.

## 10. Как уменьшать размер и что именно сравнивать

1. Начать с минимальной оболочки и **свежего** веб-билда. Исключить накопленные старые файлы из `dist` и целевого каталога Android-assets.
2. Сохранить OGG-ресурсы из `src/assets/sounds/optimized`; исходные WAV и неиспользуемые звуки в APK не копировать.
3. Проверить зависимости и анализ бандла. Разделение JS на чанки может ускорить первый экран, но само по себе не гарантирует меньший общий APK. Показатель gzip из Vite не равен размеру установленного приложения.
4. Включить release shrinking Android-кода и ресурсов с необходимыми keep rules. **R8 не вырезает неиспользуемые куски JS и произвольные файлы из `assets/www`** — веб-часть нужно подготавливать отдельно. [Уменьшение Android-приложения](https://developer.android.com/topic/performance/reduce-apk-size).
5. Для Tauri учитывать Rust-библиотеки и ABI. Для WebView/Capacitor не добавлять сторонние native SDK и плагины без задачи.
6. Сравнить минимум три числа: размер APK-файла, объём скачивания из магазина и место после установки/первого запуска. Для TWA дополнительно учесть кеш веб-игры; для всех вариантов — измерять память отдельно от размера файлов.
7. Использовать Android Studio APK Analyzer или `apkanalyzer` для состава пакета. [APK Analyzer CLI](https://developer.android.com/tools/apkanalyzer).

   ```powershell
   # После установки Android SDK Command-Line Tools и настройки PATH.
   apkanalyzer apk file-size .\game-release.apk
   apkanalyzer files list .\game-release.apk
   ```

8. APK подходит для прямой установки и тестирования. Для новых приложений Google Play используется **Android App Bundle (AAB)**; магазин генерирует подходящие APK под устройства. AAB не является файлом для обычной установки тапом на телефоне. Release-артефакты требуют настроенной подписи. [Android App Bundles](https://developer.android.com/guide/app-bundle), [подпись приложения](https://developer.android.com/studio/publish/app-signing).

## 11. Могу ли я работать с Android Studio и командами

**Да: я могу подготовить Android-проект, править Kotlin/Java/Gradle и конфигурации, запускать сборку, читать ошибки, устанавливать APK через ADB и анализировать логи.** Для сборки обычно не нужно нажимать кнопки в IDE: её терминал и обычный PowerShell запускают тот же Gradle Wrapper.

Установленную Android Studio можно запускать для открытия проекта. Работа с её окнами и эмулятором зависит от доступного подключения к рабочему столу в конкретной сессии; основной воспроизводимый путь — Gradle/ADB/CLI. Подтверждение USB-отладки на физическом телефоне и фактическое подключение устройства потребуют доступа к самому устройству.

Проверка этого компьютера на дату документа:

- Node.js **24.11.1** доступен.
- В PATH найдена Java **1.8.0_401**. Для современной Android-среды нужно выбрать совместимый JDK, обычно поставляемый с Android Studio, и настроить Gradle на него.
- Android Studio **не найдена в проверенных стандартных каталогах** `C:\Program Files\Android\Android Studio` и `%LOCALAPPDATA%\Programs\Android Studio`. Это не исключает установку в другом месте.
- SDK не найден в `%LOCALAPPDATA%\Android\Sdk`, переменные `ANDROID_HOME`/`ANDROID_SDK_ROOT` не заданы; `adb` не найден в PATH.
- Поэтому сейчас готовность Android-среды не подтверждена. Установка инструментов, запуск IDE и сборка APK в рамках этого пункта не выполнялись.

Пример дальнейшей работы после настройки SDK/JDK и подключения телефона:

```powershell
adb devices
# Затем из папки Android-проекта:
.\gradlew.bat assembleDebug
.\gradlew.bat installDebug
# Диагностика установленной игры:
adb logcat
```

## 12. Последовательность после выбора

1. Выбрать **A** для минимальной автономной оболочки или **B** для готовой интеграции. C/D выбирать при соответствующих дополнительных целях.
2. Подготовить среду и чистый Android-билд веб-игры.
3. Собрать минимальный debug APK и проверить на одном реальном телефоне WebGL 2, офлайн, звук и жесты.
4. Довести lifecycle/Back/сохранения и выполнить полный набор из раздела 9.
5. Получить подписанный release APK, записать реальный размер и производительность. Если размер оболочки не устраивает, сравнить A и B на одинаковом игровом билде.
6. После этого готовить способ распространения; для Google Play — отдельный AAB. Шаги iOS планировать отдельным документом.
